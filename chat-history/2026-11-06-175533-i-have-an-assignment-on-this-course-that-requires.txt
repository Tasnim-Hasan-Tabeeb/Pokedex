  Pokédex route

  Follow the Figma design (https://www.figma.com/design/dsgGXcu5WELIvRW90m5308/P
  ok%C3%A9mon-Code-Challenge?node-id=1-2) closely (type colours, font, spacing,
  icons). The data comes from PokeAPI, and you add one feature of your own
  design. Each heading below is one feature, which means one spec file and one
  GitHub issue.

  - List: all ~1300 Pokémon, live from the API. It must load fast and scroll
    smoothly.
  - Search:
    - The search field is as in the design, and results show while you type.
    - Part of a name is enough, in any case ("pika" finds Pikachu).
    - It finds Pokémon you haven't scrolled to yet.
    - Results look like the list rows, and no match shows an empty state.
    - PokeAPI has no search endpoint, so you have to work out how to do this.
  - Detail:
    - It is reachable from the list and from favorites.
    - It shows name, number, artwork, and types in the type colour.
    - It has three quick-switch parts: about, stats, evolution chain.
    - The evolution chain comes from the API and you can tap through to the next
      detail.
    - You can favorite and unfavorite.
  - Favorites: an own screen that persists after a restart and has an empty
    state.
  - Compare (your own design): put any two Pokémon side by side and see who is
    stronger on each stat. Figma has no screen for this, so follow its style.
  - Constraints for every feature:
    - Loading and error states on the list, detail and evolution chain.
    - The design's font loaded with Expo Font (fonts.zip
      (inholland-react-native-course-main/exam/assets/fonts.zip)).

  Technical core (required)

  - It runs in Expo Go via QR code.
  - Live data goes through TanStack Query, with no key in the repo.
  - There are at least 2 screens with Expo Router.
  - Something is stored in SQLite and survives a restart.
  - Every load has a loading state and an error state.
  - There is at least 1 native feature (Share, haptics, camera, ...).
  - TypeScript and ESLint have no errors.
  - UI, data and logic are not mixed.

  Before you build, write two choices in specs/product.md, each with the
  alternative and why. One is what you store in SQLite, and the other is which
  native feature you use.
